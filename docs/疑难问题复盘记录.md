# 文档目录勾选状态丢失问题复盘

## 1. 问题背景

- 功能：个人文档保存与载入时，左侧“文档目录”树的勾选状态应该被记住。
- 目标体验：
  - 用户在目录中取消勾选部分章节（隐藏这些章节）后点击“保存”。
  - 之后从“文档列表”中点击“载入”同一文档时：
    - 目录树应展示完整原始标题结构。
    - 之前隐藏的章节/标题应“可见但未勾选”，方便继续调整。

实际用户反馈：载入文档后，之前隐藏的章节/标题的勾选框仍然全部为勾选状态，导致“隐藏状态”无法被恢复。

## 2. 现象与复现场景

复现步骤：

1. 登录系统，上传一个包含多级标题的 DOCX（例如 1.docx）。
2. 等目录解析完成，在左侧目录中取消勾选若干章节/标题。
3. 点击右上角“保存”，等待个人文档列表出现该文档记录。
4. 打开“文档列表” Drawer，点击该文档卡片上的“载入”。

观察到的错误行为：

- 载入后目录树中的标题完整显示，但所有勾选框都被勾选。
- 用户之前隐藏的章节/标题重新被视为“选中”，与保存时的筛选状态不一致。

## 3. 技术原因分析

问题分为两个层面：

### 3.1 勾选状态持久化设计

为实现“记住勾选状态”，我们在 Supabase `documents.metadata` 中增加了字段：

- `versions`: 版本历史数组。
- `selectedKeys`: 最近一次保存时勾选的目录节点 key 列表。

保存时的设计（抽象）：

- `SavePersonalDocumentInput` 中包含 `selectedKeys: string[]`。
- 在 `savePersonalDocument` 中将其写入 `metadata.selectedKeys`。

载入时的设计（抽象）：

- `loadPersonalDocument` 从 `metadata.selectedKeys` 中读出历史勾选集合。
- 在点击“载入”时，通过 `useDocStore.setInitialCheckedKeys(selectedKeys)` 将其存入前端状态。
- Dashboard 在解析 DOCX 后，应优先用 `initialCheckedKeys` 来设置 `checkedKeys`，否则默认全选。

从设计上看，这条链路是合理的，问题在于实现细节。

### 3.2 useEffect 依赖导致的二次覆盖

Dashboard 中解析目录并设置勾选状态的逻辑：

```ts
useEffect(() => {
  if (!currentFile) {
    setHeadings([]);
    setCheckedKeys([]);
    return;
  }

  const parse = async () => {
    const root = await parseDocumentHeadings(currentFile);
    setHeadings(root);
    const allKeys = getAllKeys(root);
    if (initialCheckedKeys && initialCheckedKeys.length > 0) {
      const nextKeys = initialCheckedKeys.filter((key) =>
        allKeys.includes(key),
      );
      setCheckedKeys(nextKeys);
      setInitialCheckedKeys(null);
    } else {
      setCheckedKeys(allKeys);
    }
  };

  parse();
}, [currentFile, setParsing, setHeadings, setCheckedKeys, initialCheckedKeys, setInitialCheckedKeys]);
```

从 PersonalDocumentList 中“载入”一个文档时调用顺序为：

1. `setInitialCheckedKeys(selectedKeys)`  
   由 `loadPersonalDocument` 返回的 `selectedKeys`（上次保存的勾选集合）。
2. `setFile(file)`  
   更新 `currentFile` 导致 Dashboard 的 `useEffect` 触发。

实际行为：

1. 第一次触发 `useEffect`：
   - `initialCheckedKeys` 为非空数组（例如 `['A', 'B']`）。
   - 解析目录后，`setCheckedKeys(['A', 'B'])`（正确），随后 `setInitialCheckedKeys(null)`。
2. 由于依赖中包含 `initialCheckedKeys`，`setInitialCheckedKeys(null)` 再次触发 `useEffect`：
   - 这一次 `initialCheckedKeys` 为 `null`。
   - 走 `else` 分支执行 `setCheckedKeys(allKeys)`。

最终结果：

- 第一次设置的“按历史勾选恢复”的状态被第二次 `useEffect` 覆盖为“全选”。
- 用户看到的就是“所有标题又都勾上了”，即便之前隐藏过部分章节。

根因总结：

- `useEffect` 依赖项包含 `initialCheckedKeys`，导致在清理该状态时又重新跑了一遍“默认全选”的逻辑，覆盖了刚刚恢复的勾选状态。

## 4. 解决方案与最终实现

### 4.1 修正 useEffect 的触发条件

关键改动：**仅在 `currentFile` 变化时触发目录解析与勾选恢复**，避免 `initialCheckedKeys` 的变化触发二次覆盖。

修改前的依赖：

```ts
}, [currentFile, setParsing, setHeadings, setCheckedKeys, initialCheckedKeys, setInitialCheckedKeys]);
```

修改后的依赖：

```ts
}, [currentFile, setParsing, setHeadings, setCheckedKeys]);
```

配合原有逻辑：

- 如果 `initialCheckedKeys` 非空：
  - 使用 `initialCheckedKeys ∩ allKeys` 作为新的 `checkedKeys`。
  - 调用 `setInitialCheckedKeys(null)` 仅仅是将初始状态用完并清理，**不再触发第二轮 useEffect**。
- 否则：
  - 采用默认行为：目录全选。

这样可以保证：

- 载入时，历史勾选状态只会被应用一次，不会被后续的“全选逻辑”覆盖。

### 4.2 继续使用 metadata.selectedKeys 持久化状态

之前为支持“记住勾选状态”已经实现的逻辑保持不变：

- 保存时：
  - 后端 `DocumentMetadata` 中的 `selectedKeys` 字段始终写入当前勾选集合。
- 载入时：
  - `loadPersonalDocument` 读取 `selectedKeys` 并返回。
  - PersonalDocumentList 调用 `setInitialCheckedKeys(selectedKeys)` 将其注入到文档状态。

修复 useEffect 依赖后，这条链路可以稳定地把“上一次保存时的勾选状态”恢复到目录树上。

## 6. 经验与改进建议

1. **涉及“初始状态”的逻辑，慎重处理 useEffect 依赖项**
   - 类似 `initialCheckedKeys` 这类“只应用一次”的状态，不应出现在解析/初始化 effect 的依赖中。
   - 推荐模式：在 effect 内部读取一次并清理，而不是把清理动作本身作为触发条件。

2. **状态恢复链路要“首尾闭环”验证**
   - 本次问题的根因不是没有写入元数据，而是“写入的状态被后续逻辑覆盖”。
   - 对这种“保存 → 载入 → 恢复 UI 状态”的链路，建议检查四个环节：
     1. 保存时是否写入了完整状态。
     2. 载入时是否正确读取。
     3. 状态是否正确注入前端状态管理。
     4. UI 初始化是否只应用一次，而不会被后续逻辑覆盖。

3. **多源触发的 useEffect 尽量拆分职责**
   - 当前 `useEffect` 既负责解析文档又负责设置勾选状态，本身就较重。
   - 当依赖较多时，容易出现“一个依赖的变化触发了不该执行的逻辑”。
   - 今后可以考虑：
     - 一个 effect 专门响应 `currentFile`，只做解析；
     - 另一个 effect 响应“解析完成 + initialCheckedKeys”，只做状态恢复。

4. **尽量用单测覆盖“状态恢复”这类逻辑**
   - 当前已有服务层与列表加载层的单测，后续可补充 Dashboard 层的“初始勾选状态恢复”单测，避免类似问题回归。

通过这次问题，可以作为后续在实现“保存 + 恢复 UI 状态（尤其是树形勾选状态）”相关功能时的参考范例。***
