# 文档目录勾选状态丢失问题复盘

## 1. 问题背景

- 功能：个人文档保存与载入时，左侧“文档目录”树的勾选状态应该被记住。
- 目标体验：
  - 用户在目录中取消勾选部分章节（隐藏这些章节）后点击“保存”。
  - 之后从“文档列表”中点击“载入”同一文档时：
    - 目录树应展示完整原始标题结构。
    - 之前隐藏的章节/标题应“可见但未勾选”，方便继续调整。

实际用户反馈：载入文档后，之前隐藏的章节/标题的勾选框仍然全部为勾选状态，导致“隐藏状态”无法被恢复。

## 2. 现象与复现场景

复现步骤：

1. 登录系统，上传一个包含多级标题的 DOCX（例如 1.docx）。
2. 等目录解析完成，在左侧目录中取消勾选若干章节/标题。
3. 点击右上角“保存”，等待个人文档列表出现该文档记录。
4. 打开“文档列表” Drawer，点击该文档卡片上的“载入”。

观察到的错误行为：

- 载入后目录树中的标题完整显示，但所有勾选框都被勾选。
- 用户之前隐藏的章节/标题重新被视为“选中”，与保存时的筛选状态不一致。

## 3. 技术原因分析

问题分为两个层面：

### 3.1 勾选状态持久化设计

为实现“记住勾选状态”，我们在 Supabase `documents.metadata` 中增加了字段：

- `versions`: 版本历史数组。
- `selectedKeys`: 最近一次保存时勾选的目录节点 key 列表。

保存时的设计（抽象）：

- `SavePersonalDocumentInput` 中包含 `selectedKeys: string[]`。
- 在 `savePersonalDocument` 中将其写入 `metadata.selectedKeys`。

载入时的设计（抽象）：

- `loadPersonalDocument` 从 `metadata.selectedKeys` 中读出历史勾选集合。
- 在点击“载入”时，通过 `useDocStore.setInitialCheckedKeys(selectedKeys)` 将其存入前端状态。
- Dashboard 在解析 DOCX 后，应优先用 `initialCheckedKeys` 来设置 `checkedKeys`，否则默认全选。

从设计上看，这条链路是合理的，问题在于实现细节。

### 3.2 useEffect 依赖导致的二次覆盖

Dashboard 中解析目录并设置勾选状态的逻辑：

```ts
useEffect(() => {
  if (!currentFile) {
    setHeadings([]);
    setCheckedKeys([]);
    return;
  }

  const parse = async () => {
    const root = await parseDocumentHeadings(currentFile);
    setHeadings(root);
    const allKeys = getAllKeys(root);
    if (initialCheckedKeys && initialCheckedKeys.length > 0) {
      const nextKeys = initialCheckedKeys.filter((key) =>
        allKeys.includes(key),
      );
      setCheckedKeys(nextKeys);
      setInitialCheckedKeys(null);
    } else {
      setCheckedKeys(allKeys);
    }
  };

  parse();
}, [currentFile, setParsing, setHeadings, setCheckedKeys, initialCheckedKeys, setInitialCheckedKeys]);
```

从 PersonalDocumentList 中“载入”一个文档时调用顺序为：

1. `setInitialCheckedKeys(selectedKeys)`  
   由 `loadPersonalDocument` 返回的 `selectedKeys`（上次保存的勾选集合）。
2. `setFile(file)`  
   更新 `currentFile` 导致 Dashboard 的 `useEffect` 触发。

实际行为：

1. 第一次触发 `useEffect`：
   - `initialCheckedKeys` 为非空数组（例如 `['A', 'B']`）。
   - 解析目录后，`setCheckedKeys(['A', 'B'])`（正确），随后 `setInitialCheckedKeys(null)`。
2. 由于依赖中包含 `initialCheckedKeys`，`setInitialCheckedKeys(null)` 再次触发 `useEffect`：
   - 这一次 `initialCheckedKeys` 为 `null`。
   - 走 `else` 分支执行 `setCheckedKeys(allKeys)`。

最终结果：

- 第一次设置的“按历史勾选恢复”的状态被第二次 `useEffect` 覆盖为“全选”。
- 用户看到的就是“所有标题又都勾上了”，即便之前隐藏过部分章节。

根因总结：

- `useEffect` 依赖项包含 `initialCheckedKeys`，导致在清理该状态时又重新跑了一遍“默认全选”的逻辑，覆盖了刚刚恢复的勾选状态。

## 4. 解决方案与最终实现

### 4.1 修正 useEffect 的触发条件

关键改动：**仅在 `currentFile` 变化时触发目录解析与勾选恢复**，避免 `initialCheckedKeys` 的变化触发二次覆盖。

修改前的依赖：

```ts
}, [currentFile, setParsing, setHeadings, setCheckedKeys, initialCheckedKeys, setInitialCheckedKeys]);
```

修改后的依赖：

```ts
}, [currentFile, setParsing, setHeadings, setCheckedKeys]);
```

配合原有逻辑：

- 如果 `initialCheckedKeys` 非空：
  - 使用 `initialCheckedKeys ∩ allKeys` 作为新的 `checkedKeys`。
  - 调用 `setInitialCheckedKeys(null)` 仅仅是将初始状态用完并清理，**不再触发第二轮 useEffect**。
- 否则：
  - 采用默认行为：目录全选。

这样可以保证：

- 载入时，历史勾选状态只会被应用一次，不会被后续的“全选逻辑”覆盖。

### 4.2 继续使用 metadata.selectedKeys 持久化状态

之前为支持“记住勾选状态”已经实现的逻辑保持不变：

- 保存时：
  - 后端 `DocumentMetadata` 中的 `selectedKeys` 字段始终写入当前勾选集合。
- 载入时：
  - `loadPersonalDocument` 读取 `selectedKeys` 并返回。
  - PersonalDocumentList 调用 `setInitialCheckedKeys(selectedKeys)` 将其注入到文档状态。

修复 useEffect 依赖后，这条链路可以稳定地把“上一次保存时的勾选状态”恢复到目录树上。

## 6. 经验与改进建议

1. **涉及“初始状态”的逻辑，慎重处理 useEffect 依赖项**
   - 类似 `initialCheckedKeys` 这类“只应用一次”的状态，不应出现在解析/初始化 effect 的依赖中。
   - 推荐模式：在 effect 内部读取一次并清理，而不是把清理动作本身作为触发条件。

2. **状态恢复链路要“首尾闭环”验证**
   - 本次问题的根因不是没有写入元数据，而是“写入的状态被后续逻辑覆盖”。
   - 对这种“保存 → 载入 → 恢复 UI 状态”的链路，建议检查四个环节：
     1. 保存时是否写入了完整状态。
     2. 载入时是否正确读取。
     3. 状态是否正确注入前端状态管理。
     4. UI 初始化是否只应用一次，而不会被后续逻辑覆盖。

3. **多源触发的 useEffect 尽量拆分职责**
   - 当前 `useEffect` 既负责解析文档又负责设置勾选状态，本身就较重。
   - 当依赖较多时，容易出现“一个依赖的变化触发了不该执行的逻辑”。
   - 今后可以考虑：
     - 一个 effect 专门响应 `currentFile`，只做解析；
     - 另一个 effect 响应“解析完成 + initialCheckedKeys”，只做状态恢复。

4. **尽量用单测覆盖“状态恢复”这类逻辑**
   - 当前已有服务层与列表加载层的单测，后续可补充 Dashboard 层的“初始勾选状态恢复”单测，避免类似问题回归。

通过这次问题，可以作为后续在实现”保存 + 恢复 UI 状态（尤其是树形勾选状态）”相关功能时的参考范例。

# 跨浏览器载入文档解密失败问题复盘

## 1. 问题背景

- 功能：用户在浏览器 A 保存个人文档后，在浏览器 B（新浏览器 / 无本地密钥）载入该文档。
- 目标体验：
  - 新浏览器登录后，系统自动从服务端恢复用户私钥。
  - 私钥恢复成功后，即可正常解密并载入之前保存的文档。

实际用户反馈：在新浏览器中载入之前保存的文档时，始终报错”文档解密失败”。

## 2. 现象与复现场景

复现步骤：

1. 在浏览器 A 登录，上传并保存一份 DOCX 文档（加密上传成功）。
2. 在浏览器 A 中多次载入该文档，均正常。
3. 打开浏览器 B（或浏览器 A 的隐身窗口），登录同一账号。
4. 打开”文档列表”，点击该文档的”载入”。

观察到的错误行为：

- 始终报”载入文档失败：文档解密失败”或类似错误信息。
- Supabase 日志中 `key-restore` Edge Function 有正常调用记录（说明私钥恢复 API 被调用且返回了数据）。
- 但 `r2-sign-download` Edge Function **没有任何日志**（说明流程在下载前就已中断）。

## 3. 技术原因分析

### 3.1 文档载入的完整链路

`loadPersonalDocument` 的执行顺序：

1. 读取 `documents` 表元数据
2. 读取 `document_versions` 表获取最新版本的 `r2_key` 和 `encrypted_meta`
3. 读取 `document_keys` 表获取 `wrapped_document_key`
4. 从 IndexedDB 获取用户密钥对（`getUserKeyPair`）
5. 用私钥解封 `wrappedKey`（`unwrapDocumentKey`）← **失败点**
6. 调用 `r2-sign-download` 获取预签名 URL，从 R2 下载加密 Blob ← **未到达**
7. 用文档密钥解密 Blob

因为步骤 5 失败，流程在到达步骤 6 之前就抛出异常，所以 `r2-sign-download` 没有产生日志。

### 3.2 根本原因：`restoreUserPrivateKey` 中的 JWK `key_ops` 字段处理错误

问题出在 `web/src/services/cryptoKeyService.ts` 的 `restoreUserPrivateKey` 函数。

该函数从服务端恢复私钥后，需要从私钥 JWK 中派生出公钥 JWK，以便同时保存公钥到 IndexedDB。派生逻辑是浅拷贝私钥 JWK 并删除私有字段（`d`、`dp`、`dq`、`p`、`q`、`qi`）。

**关键错误**：删除私有字段后，**没有更新 `key_ops` 字段**。

私钥的 JWK 中 `key_ops` 为 `['decrypt']`，而公钥导入时需要 `usages: ['encrypt']`。Web Crypto API 要求 `usages` 参数必须是 `key_ops` 的子集。因此：

```
key_ops: ['decrypt']  +  usages: ['encrypt']
→ 'encrypt' ∉ ['decrypt']
→ 抛出 DataError
```

错误代码（修复前）：

```ts
const publicJwk: JsonWebKey = { ...jwk };
delete publicJwk.d;
delete publicJwk.dp;
delete publicJwk.dq;
delete publicJwk.p;
delete publicJwk.q;
delete publicJwk.qi;
// ❌ key_ops 仍然是 ['decrypt']，导入公钥时 usages=['encrypt'] 不匹配

const publicKey = await crypto.subtle.importKey(
  'jwk',
  publicJwk,
  { name: 'RSA-OAEP', hash: 'SHA-256' },
  true,
  ['encrypt'],  // ❌ 与 key_ops: ['decrypt'] 冲突 → DataError
);
```

### 3.3 次要问题：私钥导入时 `extractable` 设为 `false`

同一函数中，私钥在导入时设置了 `extractable: false`：

```ts
const privateKey = await crypto.subtle.importKey(
  'jwk',
  jwk,
  { name: 'RSA-OAEP', hash: 'SHA-256' },
  false,  // ❌ 不可导出，后续 re-export 会静默失败
  ['decrypt'],
);
```

这意味着恢复的私钥无法通过 `crypto.subtle.exportKey()` 重新导出，影响后续的密钥备份更新操作（如 `backupUserPrivateKey`）。

### 3.4 完整故障链

在新浏览器中，失败链路如下：

1. 用户登录 → `ensureUserKeyPair()` 被异步触发
2. IndexedDB 中无密钥 → 调用 `restoreUserPrivateKey()`
3. `key-restore` Edge Function 成功返回私钥 JWK（Supabase 有日志）
4. 私钥导入成功（`['decrypt']` 与 JWK 匹配）
5. 派生公钥 JWK 时 `key_ops` 未更新 → 公钥导入抛出 `DataError`
6. `catch` 块返回 `null` → 密钥未保存到 IndexedDB
7. `ensureUserKeyPair()` 检测到”恢复失败” → **生成全新密钥对**
8. 新密钥对通过 `backupUserPrivateKey()` 上传到服务端，**覆盖原始备份**（`keyVersion=1`，`onConflict: “user_id,key_version”` 导致 upsert 覆盖）
9. 用户点击”载入” → `unwrapDocumentKey` 用新私钥解封旧 `wrappedKey` → **解密失败**
10. 失败发生在 R2 下载之前 → `r2-sign-download` 无日志

## 4. 解决方案与最终实现

### 4.1 修复 `key_ops` 字段处理

在派生公钥 JWK 时，先删除旧 `key_ops`，再设置正确值：

```ts
const publicJwk: JsonWebKey = { ...jwk };
delete publicJwk.d;
delete publicJwk.dp;
delete publicJwk.dq;
delete publicJwk.p;
delete publicJwk.q;
delete publicJwk.qi;
delete publicJwk.key_ops;           // ✅ 删除私钥的 key_ops
publicJwk.key_ops = ['encrypt'];    // ✅ 设置公钥正确的 key_ops

const publicKey = await crypto.subtle.importKey(
  'jwk',
  publicJwk,
  { name: 'RSA-OAEP', hash: 'SHA-256' },
  true,
  ['encrypt'],  // ✅ 现在与 key_ops: ['encrypt'] 匹配
);
```

### 4.2 修复 `extractable` 参数

将私钥导入的 `extractable` 改为 `true`，使恢复的密钥可以被重新导出用于备份等操作：

```ts
const privateKey = await crypto.subtle.importKey(
  'jwk',
  jwk,
  { name: 'RSA-OAEP', hash: 'SHA-256' },
  true,    // ✅ 改为 true，保持与 ensureUserKeyPair 生成时一致
  ['decrypt'],
);
```

### 4.3 修改文件与位置

- 文件：`web/src/services/cryptoKeyService.ts`
- 函数：`restoreUserPrivateKey`（约第 115-160 行）
- 改动量：2 行修改 + 2 行新增

## 6. 经验与改进建议

1. **Web Crypto API 的 `key_ops` 字段在 JWK 转换时必须同步更新**
   - `key_ops` 约束了密钥允许的操作；从私钥 JWK 派生公钥 JWK 时，不能只删除私有字段，还必须把 `key_ops` 从 `['decrypt']` 改为 `['encrypt']`。
   - 如果不确定目标 `key_ops`，可以直接删除该字段让 Web Crypto 自动推断。

2. **`extractable` 参数要与密钥生命周期保持一致**
   - 如果密钥需要在后续被 `exportKey()` 导出（用于备份、分发、序列化等），导入时必须设置 `extractable: true`。
   - `extractable: false` 不会在导入时报错，只会在后续 `exportKey()` 时静默失败，极难排查。

3. **静默 catch 是跨浏览器问题的最大障碍**
   - 本次问题中，`restoreUserPrivateKey` 的 `catch` 块返回 `null`，`ensureUserKeyPair` 的 `catch` 块为空。多层静默 catch 导致：
     - 没有任何错误日志。
     - 错误被”恢复”为”正常的密钥不存在”，触发了”生成新密钥”分支。
     - 新密钥覆盖了原始备份，使问题从”可恢复”变为”不可恢复”。
   - 建议：在 `catch` 中至少做 `console.warn` 级别的日志，对密钥相关操作更应如此。

4. **密钥备份覆盖策略需要更安全的设计**
   - 当前 `backupUserPrivateKey` 使用 `keyVersion=1` 并通过 `onConflict: “user_id,key_version”` 做 upsert，意味着任何新生成的密钥对都会覆盖原始备份。
   - 更安全的策略：在覆盖前检查是否有文档使用旧密钥，或在 `key_version` 上做递增而非固定值，避免”断链”。

5. **排查”日志缺失”问题时，从调用链顺序入手**
   - 本次 `r2-sign-download` 无日志，并不是因为 R2 服务有问题，而是流程在更早的步骤（密钥解封）就已中断。
   - 遇到”某个环节没有日志”时，优先检查该环节的前置步骤是否有异常，而非假设该环节本身有问题。
